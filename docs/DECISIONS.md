# Decisiones de diseño

Registro de decisiones tomadas cuando el prompt (`CLAUDE.md`) era ambiguo o requería concretar algo. Regla: la opción más simple que cumple el criterio de aceptación.

| # | Tema | Decisión | Motivo |
|---|---|---|---|
| D1 | Monorepo Python | Workspace de **uv** (`pyproject.toml` raíz). `libs/chaski_common` es dependencia de ruta de cada servicio. Imágenes `python:3.12-slim`. | Un solo lockfile y venv para desarrollo; imágenes reproducibles con `uv sync --frozen`. |
| D2 | Migraciones | Una sola cadena Alembic en `db/migrations` (SQL explícito) para `core`, `ops` y `gold`. Corre el servicio `migrate` en cada `docker compose up`. | El DDL queda legible y revisable; las vistas y los grants son SQL de todas formas. |
| D3 | Roles de BD | `chaski_admin` (dueño, solo migraciones y simulador), `chaski_app` (APIs: CRUD en core/ops, lectura en gold) y `chaski_readonly` (NL2SQL: solo `SELECT` sobre las 3 vistas, `statement_timeout=10s` y transacciones de solo lectura). | Mínimo privilegio; NL2SQL no puede leer PII aunque el validador fallara. |
| D4 | Tablas y columnas extra | `ops.idempotency_keys`, `ops.raw_ingest`, `ops.quarantine_records`; `transactions.counterparty_account` (regla R4), `transactions.description`, `accounts.number`, `customers.monthly_income` (scoring), `customers.kyc_decided_*`, `complaints.requires_review`/`reviewed_at`, `loans.disbursed_at`, `audit_log.reason`/`correlation_id`, `ai_interactions.blocked_by_shields`/`provider`, `fraud_alerts.details`/`resolved_*`. | Son necesarias para cumplir endpoints y reglas del prompt. |
| D5 | Auth dev | Con `AUTH_MODE=dev`, core-api expone `POST /api/v1/dev/token` (devuelve 404 en `entra`) que firma HS256 con `DEV_JWT_SECRET`. El selector del frontend lo llama. `AUTH_MODE=dev` se **rechaza al arrancar** si `CHASKI_ENV=PROD`. | El secreto nunca llega al bundle del navegador. |
| D5b | Auth Entra | RS256 validado con JWKS del tenant (`PyJWKClient`), `aud` = `ENTRA_AUDIENCE`, `iss` v1 o v2 del tenant. Roles del claim `roles`; `customer_id` del claim `customer_id` / `extension_customer_id`. | App Roles estándar de Entra ID. |
| D6 | Auditoría | `chaski_common.audit` escribe en `ops.audit_log` en una transacción propia (sobrevive al rollback del request). Los 403 de `require_roles`/`require_customer`/ownership se auditan automáticamente. | Requisito "todo 403 se registra". |
| D7 | Config del frontend | Imagen nginx sin privilegios que genera `env.js` al arrancar desde variables `CHASKI_*`. | Misma imagen en local y Azure; solo cambian variables. |
| D8 | Analítica | `ANALYTICS_DB_URL` + `ANALYTICS_DIALECT=postgres\|tsql`. NL2SQL valida con sqlglot y transpila a T-SQL para Azure SQL. | Local usa el esquema `gold` del mismo Postgres. |
| D9 | Confirmación del asistente | ia-api nunca ejecuta `block_card`/`create_complaint`: devuelve `pending_action`; la UI confirma y llama al endpoint real de core-api. | Confirmación explícita del cliente sin estado en el servidor. |
| D10 | Herramientas del asistente | ia-api llama a cuentas-api/core-api reenviando el JWT del usuario. | El `customer_id` siempre sale del token, nunca del modelo. |
| D11 | Plazo de quejas | 15 días hábiles = lunes a viernes menos feriados nacionales de Perú (fijos + Jueves/Viernes Santo). | `chaski_common.business_days`. |
| D12 | Simulador | Carga inicial con `COPY` (≈4 s). Fechas relativas a "ahora" con semilla fija (misma estructura en cada corrida). `--live` genera tráfico **vía cuentas-api** para que pase por el motor de fraude y Eventstream. | Reproducible y realista para la demo. |
| D12b | Transferencias del simulador | Las transferencias históricas no generan el movimiento espejo en la cuenta destino. | Simplicidad; no afecta KPIs ni reglas. |
| D13 | Tests de backend | pytest contra la BD `chaski_test` del Postgres de Compose (migrada con Alembic al inicio de la sesión, tablas vaciadas por test). Si Postgres no está disponible, los tests de BD se saltan con un mensaje. | Tests reales contra Postgres sin dependencias extra. |
| D14 | UI compartida | Componentes shadcn/ui, auth, cliente API, tipos y formateadores en `packages/shared`. | Evita duplicar entre cliente y consola. |
| D15 | Rate limit | Ventana fija de 1 minuto por IP en memoria. | Suficiente con 1 réplica (scale-to-zero); con más réplicas se movería a Front Door/APIM. |
| D16 | Paquetes Python | Los paquetes se llaman `cuentas_api`, `core_api`, `ia_api`, `chaski_simulator` (no `app`/`simulator`). | Conviven en un único venv de workspace sin colisiones de nombre. |
| D17 | SQLAlchemy síncrono | Sesiones sync; FastAPI ejecuta los endpoints `def` en su threadpool. | Más simple de testear; la carga esperada es baja. |
| D18 | Logs | structlog JSON a stdout; un procesador redacta DNI, emails, teléfonos y secuencias de 13–19 dígitos en **todos** los campos (también en logs de librerías). Access log propio (método, ruta, status, duración); el de uvicorn se desactiva. | Requisito "cero PII/PAN en logs". |
| D19 | Gold local | Rentabilidad: depósitos con tasa de transferencia interna 6 % anual; préstamos/tarjetas con costo de fondeo 5 %; provisiones según bucket SBS (Normal 1 %, CPP 5 %, Deficiente 25 %, Dudoso 60 %, Pérdida 100 %). | Datos sintéticos coherentes para Insights y NL2SQL. |
| D20 | Onboarding público | `POST /onboarding` no requiere JWT (la persona aún no es cliente). Lo protegen el rate limit, la validación de imagen (tipo, firma de bytes, ≤ 5 MB) y la unicidad del DNI. En Entra se enlazaría con External ID (fuera de alcance). | El flujo del prompt empieza antes de existir el cliente. |
| D21 | Identidad de servicio | Cuando no hay token de usuario que reenviar (onboarding → ia-api), core-api usa un token de servicio: en dev, HS256 con rol `Operaciones` y 5 min de vida; en Azure, Managed Identity con el App Role `Operaciones`. | Sin roles nuevos fuera de la lista del prompt. |
| D22 | Pagos con tarjeta | `POST /card-payments` acepta solo tarjetas de **débito** (descuentan saldo de la cuenta asociada). La tarjeta de crédito no tiene libro de consumos en el modelo. `Idempotency-Key` es opcional aquí y obligatorio en `/transfers`. | El modelo de datos no tiene saldo utilizado de crédito. |
| D23 | Aprobación de préstamo | Cuando Riesgos aprueba, el préstamo se desembolsa en el acto (`DESEMBOLSADO`), con depósito en la cuenta en soles y el cronograma de cuotas. Si no hay cuenta en soles activa → 409. | Un paso menos en la demo; el estado `APROBADO` queda para datos históricos. |
| D24 | Motor de fraude y libro compartidos | `chaski_common.ledger` y `chaski_common.fraud` los usan cuentas-api y la demo "ráfaga de fraude" de core-api, que funciona igual con Entra (no necesita emitir tokens de cliente). Una sola alerta R1 por ráfaga (deduplicada en la ventana de 2 min). | El mismo motor en ambos caminos. |
| D25 | Webhook de Fabric | HMAC-SHA256 del cuerpo crudo en `X-Chaski-Signature: sha256=<hex>`, comparación en tiempo constante; las firmas inválidas se auditan. Sin protección anti-replay por timestamp (mejora futura). | Requisito del prompt con la opción más simple. |
| D26 | "Hoy" | Los KPIs usan el día calendario de Lima (`America/Lima`). | Coincide con lo que ve el negocio. |
| D27 | Pipeline local | `POST /ops/pipelines/run` sin variables de Azure valida `ops.raw_ingest` con 6 checks, manda las filas malas a `ops.quarantine_records` y registra la corrida y sus checks. Con `AZURE_SUBSCRIPTION_ID` + `AZURE_RESOURCE_GROUP` + `PIPELINE_JOB_NAME`, inicia el Container Apps Job por ARM con Managed Identity. | |
| D28 | Versiones frontend | React 18.3 (lo exige el prompt) → **react-router 7.18** (la v8 requiere React 19) y **TypeScript 5.9** (typescript-eslint aún no soporta 6+). Tailwind v4 con tokens CSS; componentes estilo shadcn/ui escritos sobre Radix en `packages/shared`. | Compatibilidad de peer dependencies. |
| D29 | MSAL bajo demanda | `@azure/msal-*` vive en `auth/entra.tsx` y se carga con `lazy()` solo si `authMode=entra`: el bundle inicial baja de 625 kB a 333 kB. | Rendimiento en móvil. |
| D30 | Plazo regulatorio en hora de Lima | `regulatory_deadline()` cuenta los 15 días hábiles sobre el calendario de Lima y vence a las 23:59:59 de Lima. Un reclamo hecho a las 23:50 del jueves ya no empieza a contar desde el viernes (hora UTC). | Bug detectado en la prueba E2E: el vencimiento caía en domingo. |
| D31 | Errores 500 con CORS | `UnhandledErrorMiddleware` convierte excepciones en JSON 500 **dentro** del middleware CORS; antes el navegador veía un error de red sin mensaje. | Bug detectado en la prueba E2E. |
| D32 | Config de las webs | `env.js` y las cabeceras de seguridad (CSP con `connect-src` limitado a las APIs) se generan al arrancar nginx. Los valores con `"`, `\`, `<` o `>` hacen fallar el arranque en lugar de escaparse. | Evita inyección en `env.js`. |
| D33 | PWA | El service worker cachea solo el shell estático; nunca `env.js` ni llamadas a la API (los saldos siempre son en vivo). Icono SVG (`sizes: any`). | Banca: sin datos obsoletos offline. |
| D34 | Tabla de módulos y roles | `apps/consola/src/modules.ts` es la única fuente (sidebar, guard y tests). Se aplica **literal** la tabla del prompt: p. ej. Admin no ve Préstamos ni Chaski Guard. Ocultar un módulo es UX; la API vuelve a validar el rol. Un test reescribe la tabla del prompt de forma independiente para detectar desvíos. | Sección 10 del prompt. |
| D35 | Rol activo | Si el token trae varios App Roles (Entra), el header muestra un selector de "rol activo" y la consola filtra por ese rol. | "rol activo" del prompt. |
| D36 | Centro de Quejas IA | Se implementa en F5 junto con el clasificador; F4 lo muestra como "en construcción". | No figura en F4 ni en F6 del plan del prompt. |
| D37 | Polling | KPIs cada 15 s y Chaski Guard cada 5 s. Guard sigue consultando en segundo plano (monitor en vivo); el resto se pausa con la pestaña oculta. | Sección 10; costo bajo. |
| D38 | Fechas de calendario | `formatDate("1994-03-21")` no aplica zona horaria (antes mostraba el 20 en Lima). Las fechas-hora sí se muestran en hora de Lima. | Bug detectado en la prueba E2E. |
| D39 | KYC en modo mock | El mock de Document Intelligence no lee la imagen: "lee" los datos que el cliente escribió (core-api los envía como `expected_*`, Azure los ignora). Es determinista por imagen: 1 de cada 5 simula un dígito del DNI mal leído y confianza baja, para demostrar las alertas de "no coincide". | La demo de onboarding necesita datos extraídos sin Azure. |
| D40 | Prompt Shields antes del modelo | Si Prompt Shields detecta un ataque, el texto **no se envía al LLM**: la queja queda `OTRO / ALTA / confianza 0 / sospechosa` con revisión humana obligatoria, el asistente responde una negativa y NL2SQL devuelve 422. Todo se registra con `blocked_by_shields=true`. | Más seguro y más barato que clasificar texto hostil. |
| D41 | Validador de cifras | `ia_api.numbers`: todo número del texto debe coincidir con un dato de origen (con redondeo de 0 a 2 decimales o expresado en miles/millones). Se usa en el resumen ejecutivo (si falla: `requiere_revision`, no se publica) y en el asistente (si falla: se reemplaza por una respuesta armada con los datos de las herramientas). Incluso el umbral "30 días" de la mora va como KPI explícito. | Prompt 8.3 y 8.4: la IA nunca inventa cifras. |
| D42 | Score de préstamo | Score base por reglas de 300 a 900 (endeudamiento, historial, nivel de riesgo, segmento y plazo), con factores explicables. El LLM solo redacta la explicación a partir de esos factores; si la IA no responde, se usan los factores como explicación. Recomendación APROBAR, REVISAR o RECHAZAR como sugerencia. | Prompt 8.2. |
| D43 | NL2SQL en dos capas | sqlglot rechaza todo lo que no sea una consulta sobre las 3 vistas (DML/DDL, `SELECT INTO`, funciones peligrosas, `pg_catalog`, CTE y subconsultas sobre otras tablas) y fuerza `LIMIT 500` (o `TOP 500` en T-SQL). Además se ejecuta con `chaski_readonly` y `statement_timeout` de 10 s, que tampoco podría leer PII aunque el validador fallara (lo prueba un test). | Defensa en profundidad. |
| D44 | SDK openai 3.x | `chat.completions` con `response_format=json_schema (strict)`, `tools` y `temperature=0`. Usa API key o Managed Identity (`get_bearer_token_provider`). El SDK 3 usa `httpx2`: los tests de contrato inyectan un `MockTransport` y verifican la petición exacta a Azure (ruta del deployment, `api-version`, cabeceras y cuerpo). | Verificable sin credenciales de Azure. |
| D45 | Centro de Quejas IA | Se implementó en esta fase (ver D36): cola de revisión obligatoria, quejas sospechosas, corrección de etiqueta (alimenta `human_override` y la métrica de precisión) y días hábiles restantes. | |
| D46 | Paleta de gráficos | Dos series validadas con el validador de la guía dataviz (separación CVD, piso de visión normal, banda de luminosidad, croma y contraste): claro `#1f5aa3`/`#00a94f` sobre `#ffffff`, oscuro `#3d7fd9`/`#22a861` sobre `#111d31` (los pasos de marca originales fallaban en oscuro). Tokens `--series-1` y `--series-2`. Un solo eje y, leyenda con 2 o más series, etiquetas directas, tooltip en todos los gráficos y tabla accesible (`sr-only`) por gráfico. | Guía de visualización. |
| D47 | Sin animaciones en gráficos | Las series de Recharts usan `isAnimationActive={false}`: los tableros se refrescan cada 5–15 s y, con la pestaña en segundo plano, la animación se congelaba a medio camino (barras casi vacías, líneas sin trazo). | Bug detectado en la prueba E2E; también respeta `prefers-reduced-motion`. |
| D48 | "Probar acceso indebido" | En `AUTH_MODE=dev` la consola hace la llamada **real** con un token de Marketing (403 auditado por la API). Con Entra no se pueden emitir tokens ajenos, así que `POST /demo/forbidden-access` (Admin + `DEMO_MODE`) registra la misma entrada de auditoría y lo indica como simulado. | Funciona en ambos modos. |
| D49 | Telemetría sin PII | Con `APPLICATIONINSIGHTS_CONNECTION_STRING`, se instrumentan FastAPI (sin `/health` ni `/ready`), httpx y SQLAlchemy, y se exportan los logs del logger raíz. `RedactingFilter` se agrega también al handler de OpenTelemetry: antes la redacción solo ocurría en el formateador de stdout y los logs de librerías habrían llegado sin redactar a App Insights. | Requisito "cero PII en logs". |
| D50 | Imágenes | Base `python:3.12-slim-bookworm` fijada (Microsoft publica ODBC 18 para Debian 12) con `msodbcsql18` + `pyodbc` en core-api e ia-api para Azure SQL. Todas las imágenes multi-stage, sin root (uid 10001 / nginx 101), con `HEALTHCHECK` y labels OCI. | Prompt 14. |
| D51 | Accesibilidad | axe-core en Vitest sobre 12 pantallas clave (el contraste se validó aparte sobre los tokens, porque jsdom no calcula estilos). Corrigió la jerarquía de encabezados: `CardTitle` pasó de `h3` a `h2`. | WCAG AA. |
| D52 | docs/API.md generado | `scripts/gen_api_docs.py` recorre las rutas reales (incluido el anidamiento de routers de FastAPI 0.142) y lee los roles de las dependencias `require_roles`/`require_customer`. Falla si un endpoint no tiene descripción en español. | La documentación no puede desactualizarse. |
| D53 | Postgres en CI | El job `test` levanta `postgres:16-alpine` con `docker run` **después** del checkout, montando `db/init`: se reutiliza el mismo script de roles y la BD `chaski_test` que en local. Un `services:` de Actions arranca antes del checkout y no puede montar el repo. Las contraseñas son aleatorias por ejecución y enmascaradas. `db/init/01-roles.sh` pasa a ser ejecutable en git (antes, en Linux se habría *sourceado* y su `set -u` afectaría al entrypoint). | Tests reales contra Postgres sin duplicar SQL. |
| D54 | Imagen + escaneo en un job | `image` construye con Buildx (`load: true`, caché `type=gha`) y escanea con Trivy en el mismo runner: evita mover la imagen entre jobs. Trivy falla solo con CRITICAL que tengan parche (`ignore-unfixed`); el reporte HIGH+CRITICAL completo queda como artefacto. Tag `sha-<commit completo>` vía docker/metadata-action. | Más rápido y barato en minutos de Actions. |
| D55 | Sin code scanning | Subir SARIF a Code scanning en repos privados requiere GitHub Advanced Security (no incluido en Pro): el SARIF de Trivy se publica como artefacto (14 días). | Permitido por el prompt de CI/CD. |
| D56 | Actions fijadas por SHA | Todas las actions de terceros se referencian por commit SHA con comentario de versión, y Dependabot (`github-actions`, `uv`, `docker`) propone actualizaciones semanales agrupadas. | Cadena de suministro. |
| D57 | Dependabot sin saltos mayores de imágenes | Para Docker se ignoran las actualizaciones *semver-major* (el primer PR propuso Node 22 → 26 en las webs): un cambio mayor de runtime se planifica y prueba aparte, no llega mezclado con las actualizaciones semanales. | Estabilidad. |
| D58 | Verificación del CI (C1) | Ejecutado en GitHub: push a `main` en verde (lint 22 s, tests 32 s con 71 tests y 89.8 % de cobertura, imagen + Trivy 100 s, ~2 min en paralelo). PR que toca cuentas-api en verde (#2), PR con un test roto en rojo justo en ese test (#3), PR que solo toca `apps/` sin ejecución (#4). Los PRs de prueba se cerraron sin merge. | Criterios 1–4 del prompt de CI/CD. |
| D59 | Publicación sin reconstruir | El job `image` construye, escanea y **solo en push** se asocia al environment `build` (OIDC con `AcrPush`) para subir a ACR la misma imagen escaneada (`sha-<commit>`). Los PRs construyen y escanean sin environment ni credenciales. Las credenciales federadas de Entra requieren un *subject* exacto (sin comodines como `release/*`), por eso se usan subjects por environment. | Build once, deploy many. |
| D60 | PROD sin revisores (GitHub Pro) | GitHub Pro no permite *required reviewers* en environments de repos privados (la API responde 422). Equivalente auditable: `deploy-prod` solo corre con `workflow_dispatch` (environment `prod`) sobre `main`, y GitHub registra quién lo ejecutó. La variable de repo `PROD_AUTO_DEPLOY=true` reactiva la promoción automática en el push a `main` si el plan cambia. | Limitación del plan; criterio "PROD exige decisión humana". |
| D61 | Promoción por digest | PROD despliega la imagen etiquetada `test` en ACR (por digest, no por tag) y verifica con su label `org.opencontainers.image.revision` que ese commit sea ancestro de `main`: funciona con cualquier estrategia de merge y nunca reconstruye. Los tags `dev`/`test`/`prod` se mueven con `az acr import` tras cada deploy exitoso. | Ninguna imagen llega a PROD sin pasar por TEST. |
| D62 | Deploy con rollback | Action compuesta `.github/actions/deploy-containerapp`: guarda la imagen anterior, actualiza la app, prueba `/health` y `/ready` con reintentos (240 s por el arranque en frío) y, si falla, vuelve a la imagen anterior y deja el job en rojo. Verificada con *shims* de `az`/`curl` (camino OK y rollback) y con shellcheck. | Criterio 7 del prompt de CI/CD. |
| D63 | Environments de GitHub | `build` (develop, release/*, main), `dev` (develop), `test` (release/*), `prod` (main), con políticas de rama: un deploy a un entorno solo puede salir de su rama. | Mínimo privilegio. |
| D64 | Tags de entorno con `imagetools` | Los tags `dev`/`test`/`prod` se mueven con `docker buildx imagetools create` (solo republica el manifiesto) en lugar de `az acr import`, que exige el permiso `importImage` que `AcrPush` no incluye: las identidades de deploy solo necesitan `AcrPush` en el ACR y `Contributor` sobre su propia Container App. | Mínimo privilegio. |
| D65 | Guía de CI/CD verificable | `docs/CICD.md` documenta Azure y OIDC paso a paso con una identidad administrada por environment (*subject* `repo:<repo>:environment:<env>`). Los comandos se validaron contra Azure CLI 2.90 (`--help` en la imagen oficial), los flags de `gh` contra la versión instalada, y todos los bloques bash con shellcheck. La protección de ramas queda documentada para que la aplique el dueño del repo. | Criterio 8 del prompt de CI/CD. |
| D66 | Región `westus` | La Azure Policy de la universidad solo permite 5 regiones; `eastus2` (guía) está bloqueada y Canada Central tiene cuota 0 de modelos de chat. West US tiene todos los servicios y cuota de `gpt-5-mini`. | Gobierno de la nube y disponibilidad real. |
| D67 | Webs en Container Apps | Static Web Apps no está disponible en ninguna región permitida: las webs corren en Container Apps con nginx sin root, CSP y `env.js` en runtime, detrás de API Management. | Sin perder cabeceras de seguridad. |
| D68 | Identidad en otro tenant | La universidad bloquea el registro de apps en Entra y crear un tenant Workforce exige licencia de pago: apps, App Roles y usuarios viven en el directorio de la cuenta personal (Entra ID Free); la infraestructura, en la suscripción de estudiante. Las APIs confían en ese tenant por su Tenant ID y JWKS. | Costo cero; identidad separada de la infraestructura. |
| D69 | `customer_id` en el token | Extensión de directorio de `chaski-api` emitida como claim opcional; Entra la entrega como `extn.customer_id` con valor de tipo array, que las APIs y las SPAs desenvuelven. | El cliente se identifica por el token, nunca por el body. |
| D70 | Servicio a servicio entre tenants | Entra rechaza una identidad administrada de otro tenant como credencial federada (AADSTS700236): `chaski-services` se autentica con un **certificado generado y guardado por Key Vault** (12 meses, aviso a 30 días); en Entra solo está la parte pública. | Sin secretos copiables cuando no hay federación. |
| D71 | Service endpoints | Key Vault, Storage, Azure SQL y AI aceptan solo la subred de Container Apps y la IP del admin, vía service endpoints (gratis) en vez de Private Endpoints (~USD 7/mes cada uno). PostgreSQL no tiene acceso público (VNet). Los Private Endpoints quedan como diseño objetivo. | Presupuesto de estudiante. |
| D72 | API Management Consumption | Gateway único con `validate-jwt` (Entra v2), `X-Correlation-ID` y excepciones (health, preflight, onboarding anónimo, consulta DNI anónima, webhook HMAC). `rate-limit-by-key` no existe en Consumption: el límite por IP sigue en cada API. | Defensa en profundidad sin costo fijo. |
| D73 | gpt-5-mini | Única cuota de chat disponible. Es un modelo de razonamiento: no acepta `temperature`, así que se envía `reasoning_effort=minimal` (`AZURE_OPENAI_REASONING_EFFORT`) con api-version `2025-04-01-preview`. | Disponibilidad; determinismo vía esquema estricto y validadores. |
| D74 | Pipeline como job | El flujo de la Fase 7 corre en `caj-pipeline` (botón de la consola) y `caj-pipeline-nightly` (22:00 Lima) con la imagen de core-api: checks de calidad, cuarentena, lake bronze/silver en Parquet con minimización de datos y MERGE idempotente al DW de Azure SQL (SCD2, `ROLLUP`) con token de Entra. Los checks bloqueantes impiden cargar el DW. | Sin Prefect ni servicios externos. |
| D75 | IaC desde GitHub | `infra.yml` aplica `main.bicep` con `id-chaski-github-infra` (Owner en `rg-chaski` + rol de suscripción limitado a despliegues). Sus propios permisos, el Activity log y los usuarios de Azure SQL son *bootstrap* de un Owner (`bootstrap.bicep`, `deploy.ps1 -Stage dwusers`): una identidad no se da permisos a sí misma. | Todo en la nube con separación de funciones. |
| D76 | FinOps automatizado | PostgreSQL se enciende a las 08:00 y se apaga a las 23:00 (Lima) con `pg-schedule.yml` y un rol que solo permite start/stop; Sentinel se retira solo antes de terminar su prueba gratuita (`sentinel-offboard.yml` + fecha en el Bicep); Log Analytics con tope diario y los SDK de Azure silenciados (`NOISY_LOGGERS`). | Gasto previsible de ~USD 15/mes. |
